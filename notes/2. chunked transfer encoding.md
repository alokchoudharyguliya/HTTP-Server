# Chunked transfer encoding

These are my notes on sending a file in pieces, and on how to read the size lines curl prints when `--raw` is set.

## The issue

`FileServer::readFile` copied the entire file into a string. `HTTPResponse::serialize` then glued the status line, the headers, and that body into a second string. Nothing was sent until both copies existed. A small `index.html` does not show the cost. A large file does: the process holds the file and the full response at the same time, and the client waits for the first byte until the whole read finishes.

The shape before the change:

```text
read entire file → build entire response in memory → send response
```

The shape after it:

```text
read one buffer → encode that chunk → send → repeat → send the 0 chunk
```

## The rule on the wire

Each chunk is the size of its data in hexadecimal, then `\r\n`, then the bytes, then `\r\n`. The size is not `0x5`. It is `5`. A last chunk of size 0, followed by another `\r\n`, tells the client the body is finished. There may be trailer headers between those two line endings. This server sends none, so the terminator is the five bytes `0\r\n\r\n`.

```text
HTTP/1.1 200 OK\r\n
Content-Type: text/html\r\n
Transfer-Encoding: chunked\r\n
Connection: keep-alive\r\n
\r\n
5\r\n
Hello\r\n
6\r\n
 World\r\n
0\r\n
\r\n
```

`Content-Length` and `Transfer-Encoding: chunked` must not both be present. The client would not know which rule finds the end of the body. Keep-alive is a separate header. The 0 chunk ends this body. `Connection` decides whether the socket stays open for another request.

A static file has a known size, so it could instead be streamed with `Content-Length` after a `stat`. Chunked encoding is the path that still works when the total is not known before the first byte is sent. That is the case this change is practicing.

## What changed, and what did not

`FileServer::openBinary` returns `std::ifstream(path, std::ios::binary)`. Binary mode matters because a text-mode read can change bytes, and the hex size has to be the number of bytes that will be written. The stream is a local in `handleClient`. It is not a member of `FileServer`. One `FileServer` is shared by every worker, and a member stream would be a race.

`serialize` still writes headers and `body`. That path stays for 403 and 404, which are small strings with `Content-Length`. `serializeHeaders` is the same function without `response << body`. The file path sets `Transfer-Encoding: chunked` and does not set `Content-Length`.

The read buffer is 4096 bytes. `formatChunk` builds one string: hex size, `\r\n`, the bytes, `\r\n`. `chunkTerminator` returns `0\r\n\r\n`. An early version of the loop sent the formatted chunk and then sent `fileBuffer` again, and it sent the 0 chunk after every read. That doubled the body and ended the message after the first piece. The loop now sends `formatChunk` once per read, and the terminator once after `gcount` returns 0.

`Socket::send` was already a loop, so each of those strings is written in full even when `::send` returns a short count. The socket class did not need another method for this.

## Where the pieces come from

Chunked encoding is not a macOS facility and it is not a package. It is part of HTTP itself. The client and the server agree on the framing in the message text. `Transfer-Encoding: chunked` and the hexadecimal sizes are just bytes in that message. Nothing in the kernel counts chunks. `send` still only copies a buffer. The meaning of `5\r\nHello\r\n` is interpreted by curl, or by the browser, after the bytes arrive.

The file read is the C++ standard library, also not a package that was installed for this project. `std::ifstream` is declared in `<fstream>`. `openBinary` passes `std::ios::binary` so the library does not translate line endings while it reads. `read` and `gcount` report how many bytes that call actually extracted. `std::hex` on an `ostringstream`, from `<sstream>`, prints the size in hexadecimal. `formatChunk` is ordinary string building on top of that.

The kernel is involved only at `send`. Each chunk string is a normal buffer. A short write is still the same `Socket::send` loop as any other response.

## How I read `--raw`

```bash
curl -v --http1.1 --raw http://localhost:8001/
```

`--raw` leaves the chunk size lines in the output. Without it, curl strips them and prints only the file, so a correct chunked response looks the same as a `Content-Length` response.

A file smaller than 4096 bytes is one data chunk. The first small page was 225 bytes, and 225 in hex is `e1`. The output was the headers, then `e1`, then the HTML, then `0` and a blank line. `Connection: keep-alive` was still there, and curl still said the connection was left intact.

A file larger than the buffer is several chunks. `1000` hex is 4096 decimal, one full read. The size line falls in the middle of a word (`siz` / `e line`) because the cut is every 4096 bytes, not at a newline. The last data chunk is the remainder, for example `ed5` hex, which is 3797 bytes. Then `0` and a blank line. The repeated paragraphs in that test were the contents of `index.html`, sent once and split across those chunks.

Shrinking the read buffer to 16 bytes makes the cuts obvious on a small file:

```bash
curl -N --http1.1 --raw http://localhost:8001/ | head -n 40
```

`-N` stops curl from buffering. A 2 GB file would also stream, because the whole file is never loaded, but at 4096 bytes per chunk that is about half a million size lines. It is a poor way to see the framing. A few megabytes is enough to check that the pieces add up:

```bash
dd if=/dev/zero of=public/big.bin bs=1m count=8
curl -o /dev/null -w "size=%{size_download}\n" http://localhost:8001/big.bin
```

`size` should be 8388608. The body is zeros, so the terminal stays quiet. `big.bin` is deleted after that check, and the buffer goes back to 4096.

The access log used `response.body.size()`. A streamed file leaves `body` empty, so the log said `0 B` even when the file was sent. Counting `gcount` into `bytesSent` is a later change, written up in `7. access log size and benchmark.md`.
