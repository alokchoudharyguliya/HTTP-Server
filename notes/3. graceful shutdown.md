# Graceful shutdown

These are my notes on what Ctrl+C is allowed to do, and on why the workers still need a timeout after the listening socket has already woken up.

## The issue

Ctrl+C delivers SIGINT. The default action kills the process immediately. The operating system then reclaims the sockets and the threads, but the program never gets to run its own cleanup. `accept` is still blocked, tasks already in the pool queue are abandoned, and `~ThreadPool` never reaches `join`.

There are two different waits that have to be woken, and they are not the same call:

- The main thread is blocked in `accept` on the listening socket.
- Each worker that has a keep-alive client is blocked in `recv` on that client's socket.

Stopping one of those does not stop the other. Closing the listening socket does not make an in-progress `recv` return.

## What the signal handler is allowed to do

A signal can arrive while any thread is inside any function, including one that already holds a mutex. The handler therefore must not lock, must not log through `Logger`, and must not join threads. Those can deadlock or corrupt state.

The handler does only two things that are safe there:

```text
g_stop = 1
if g_listenFd >= 0: shutdown(g_listenFd, SHUT_RDWR)
```

`g_stop` is a `volatile sig_atomic_t`. `sig_atomic_t` is the integer type the C library guarantees can be written from a handler without tearing. `volatile` stops the compiler from caching the flag in a register, so the `while (!g_stop)` loop in `start` actually re-reads it. It is not a mutex and it does not publish the rest of the program's memory. It is only the flag.

`g_listenFd` is a plain `int`, filled with `listener_.fd()` after `listen` returns. `shutdown` on that descriptor unblocks `accept`. `SHUT_RDWR` means the socket can no longer be read or written, which is enough to wake the waiter. If Ctrl+C arrives before `listen` has stored the descriptor, the flag is still set and the `if` skips `shutdown`. `start` then sees `g_stop` and does not enter the accept loop.

`main` installs this with `std::signal(SIGINT, onSigint)` before `server.start()`.

## What the main thread does once it wakes

`start` is `while (!g_stop)`. After `shutdown`, `accept` returns an invalid socket. `Socket::accept` logs `Failed to accept client` once. That line is the wake-up, not a new client failing. The loop then breaks because `!client.isValid()` or `g_stop` is set, and `listener_.close()` runs.

`start` returns, `main` returns, and the `HTTPServer` destructor runs. The pool is a member, so `~ThreadPool` runs as part of that. It sets the pool's own `stop_` under the queue mutex, `notify_all`s the condition variable, and `join`s every worker. Workers exit their loop only when `stop_` is set and the task queue is empty, so tasks that were already queued are still run. The pool did not need a new method. The process exiting `main` is what starts that destructor.

`g_stop` and `stop_` are different flags. The first one stops `accept`. The second one stops the workers from taking new tasks. Setting only `g_stop` does not wake a worker that is inside `recv`.

## Why a worker still needs a timeout

A keep-alive worker is asleep in `recv` and will not look at `stop_` until `recv` returns. Each accepted client gets `setReceiveTimeout(2)`, which is `SO_RCVTIMEO`. After 2 seconds with no bytes, `recv` returns -1 and `errno` is `EAGAIN` or `EWOULDBLOCK`.

That result is not the client leaving. The read loop treats it like this:

```text
if recv < 0:
  if errno is EAGAIN or EWOULDBLOCK and g_stop is clear:
    wait again
  else:
    return, which closes the socket
if recv == 0:
  the client closed the connection
```

During normal serving, an idle keep-alive connection survives each timeout. After Ctrl+C, `g_stop` is already 1, so the next timeout makes the worker return. `join` can then finish. Without this split, every idle client would be dropped after 2 seconds even when the server was not shutting down, because `-1 <= 0` used to be treated as disconnect.

A response that is already inside `send` is not interrupted. The worker finishes that write, loops back to `recv`, and exits on the timeout. There is no list of client descriptors for the signal handler to shut down. That is why shutdown can take about 2 seconds when clients are connected, and longer only if a large send is in progress.

## Where the signal and the timeout come from

SIGINT is not a C++ exception and it is not something the server polls for. The terminal sends it when Ctrl+C is pressed. Delivery is done by the kernel. The default action, also in the kernel, is to kill the process. `std::signal` asks the C library to register `onSigint` instead. The type `volatile sig_atomic_t` comes from the C standard, through `<csignal>`. It is the one integer type a handler is allowed to write. It is not a lock.

`shutdown` is a POSIX socket call, the same family as `accept`. It does not destroy the descriptor. It marks the connection so that a blocked `accept` or `recv` on it wakes up. The descriptor number is just an `int`. The kernel is what was sleeping inside `accept`, and `shutdown` is what wakes that sleep.

`SO_RCVTIMEO` is a socket option set with `setsockopt`, again a kernel setting on that descriptor, not a timer thread in the program. When the timeout expires, the kernel makes `recv` return -1 and sets `errno` to `EAGAIN` or `EWOULDBLOCK`. `errno` is thread-local state maintained by the C library for the call that just failed. The 2-second value is the program's choice. The wake-up is the kernel's.

`join` is different. It is a C++ thread-library wait, not a socket call. It only finishes after the worker function has returned. That is why a worker stuck in `recv` holds up process exit even after the listening socket is already closed.

## What I expect to see

Start the server, request a page so a worker is in `recv`, then press Ctrl+C.

- The accept loop logs one `Failed to accept client` line.
- The process returns to the shell instead of having to be killed.
- A new connection to port 8001 is refused, because the listening socket was closed.
- If a keep-alive client was connected, the process waits up to about 2 seconds and then exits. That wait is the worker's read timeout, not a hung `join`.
