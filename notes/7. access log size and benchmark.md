# Access log size and the benchmark

These are my notes on why a successful file response logged `0 B`, and on how to read the `wrk` numbers. The first table is the thread pool. The next section is the same commands after the kqueue loop. The last section is the `EVFILT_WRITE` checks with `big.bin`.

## The access log

`Logger::access` printed `response.body.size()`. That was correct when the whole file was stored in `body` and then serialized. Chunked responses never assign `body`. The bytes go from the `ifstream` into `formatChunk` and out through `send`. The log still ran, and it still said `0 B`, after a 200 that had just sent the page.

`bytesSent` is a local counter for that one request. It starts at 0. A 403 sets it from `<h1>403 Forbidden</h1>`, which is 21 bytes. A 404 sets it from `<h1>404 Not Found</h1>`, which is 22 bytes. The file loop adds `n` from `gcount` after each successful read. The hex size line and the `\r\n` around the data are not added. The terminating `0\r\n\r\n` is not added. The number in the log is the file, or the small error page, not the size of the framing and not the size of the header block.

The counter is updated before `send` returns. If `send` then fails, `handleClient` returns without calling `access`, so a failed write does not produce a log line for a body that only partly went out.

A 225-byte `index.html` should log `225 B`. That is the same length the earlier `Content-Length` responses used, and the same length as hex `e1` on the wire when the file fits in one chunk.

## Why `test/load_test.sh` is not the baseline

That script starts up to 1000 `curl` processes, 1000 at a time, and prints only the status code. Most of the time is creating processes, not the server. It also opens a new connection per request, so it does not measure keep-alive the way `wrk` does.

`wrk` keeps a fixed number of connections open and sends the next request as soon as the response finishes. It reports requests per second and a latency distribution. It does not show the idle-client problem from the kqueue notes, because it never leaves a connection quiet.

Two setup details changed the first commands:

- `localhost` tries `::1` first. This server listens on IPv4 only, so that attempt is "connection refused" and then curl or `wrk` falls back to `127.0.0.1`. The benchmark used `127.0.0.1` directly so the refusal is not part of the timing.
- `wrk -t4 -c1` does not start. `wrk` needs at least as many connections as threads. The message is `number of connections must be >= threads`. One connection has to be `-t1 -c1`.
- The first JPEG run printed `unable to connect to 127.0.0.1:8001 Connection refused` because the server was not listening. The second run is the one in the table.
- `LOG_LEVEL` stayed at the default `info`. `debug` would have logged every request and every header, and that time would have been inside the measurement.

Each successful run was 30 seconds. The raw output is in `bench.md`.

## Where `wrk` comes from

`wrk` is not in the server and it is not an operating-system call. It is a separate program, installed on the machine with `brew install wrk`, and it connects to the server as a client the same way curl does. The numbers in `bench.md` are `wrk`'s report about what it saw. The server does not compute requests per second or percentiles.

A percentile is `wrk` sorting the response times from that run. `50%` means half of the responses were at least this fast. `99%` means 99 percent were at least this fast, so the remaining 1 percent were slower. `Requests/sec` is the count of completed responses divided by the 30 seconds. The kernel and the server still do the sockets. `wrk` only opens many of them and times the replies.

## How to read one `wrk` block

`Requests/sec` is the throughput of the whole run. `Req/Sec` under thread stats is per `wrk` thread, so with 4 threads it is about a quarter of the total and should not be compared with `Requests/sec`.

`Transfer/sec` is bytes on the wire, headers and chunk framing included. For `/`, 244.15 MB across 771108 requests is about 330 bytes each, which is a small HTML file plus headers and the chunk wrapper. For `file.jpeg`, 16.10 GB across 651992 requests is about 26 KB each.

The latency distribution is the part that matters for the tail. `50%` is the typical response. `99%` is the tail used as the baseline. `Max` is a single outlier. On the 8-connection run of `/`, the max was 45 ms while the 99th percentile was 3.86 ms. The average is pulled toward that tail when the standard deviation is large. The JPEG run shows this clearly: the 50th percentile is 297 µs, the average is 10.13 ms, and the 99th percentile is 207 ms.

## What the thread-pool runs showed

| Target | Threads | Connections | Requests/sec | Transfer/sec | 50% | 99% |
| --- | --- | --- | --- | --- | --- | --- |
| `/` | 1 | 1 | 10,992 | 3.48 MB | 75 µs | 1.34 ms |
| `/` | 4 | 8 | 25,694 | 8.14 MB | 265 µs | 3.86 ms |
| `/` | 4 | 64 | 24,693 | 7.82 MB | 261 µs | 1.13 ms |
| `/file.jpeg` | 4 | 8 | 21,708 | 549 MB | 297 µs | 207 ms |

One connection is the floor. About 11,000 requests/sec, half of them done in 75 µs.

Eight connections do a little more than twice that work, about 25,700 requests/sec, not eight times as much. The typical response slows from 75 µs to about 265 µs once the 8 workers are shared. The pool has 8 workers, so this is the point where each worker can be busy.

Sixty-four connections do not raise throughput. Requests/sec fall slightly, to about 24,700. The 99th percentile for `/` stays in the 1–4 ms range and moved between the 8-connection sample and the 64-connection sample, so that tail is noisy for this small page. The per-thread request rate at 64 connections also swings (`Stdev 6.60k`). Eight connections already saturate `/`. Extra connections are waiting, not making the small response faster.

`file.jpeg` is a different limit. The request rate drops to about 21,700/sec while transfer rises to 549 MB/sec. Half of those responses are still near 300 µs, but about 1 in 100 takes around 207 ms. The long tail belongs to moving the larger file, not to `/`. An event loop can remove threads blocked on idle sockets. It does not, by itself, remove that 207 ms.

A later server should be compared only with the same URL, the same `-c`, another 30-second run, `info` logging, and `127.0.0.1`.

## What the kqueue runs showed

Same commands, same day, after `start` waited in `kevent` instead of handing sockets to the pool. The raw blocks are in `bench.md`. `LOG_LEVEL` was still unset.

| Target | Connections | Thread pool | kqueue |
| --- | --- | --- | --- |
| `/` | 1 | 10,992 req/s, p50 75 µs, p99 1.34 ms | 3,269 req/s, p50 187 µs, p99 56.66 ms |
| `/` | 8 | 25,694 req/s, p50 265 µs, p99 3.86 ms | 5,026 req/s, p50 1.17 ms, p99 39.44 ms |
| `/` | 64 | 24,693 req/s, p50 261 µs, p99 1.13 ms | 3,236 req/s, p50 14.75 ms, p99 1.24 s |
| `/file.jpeg` | 8 | 21,708 req/s, 549 MB/s, p99 207 ms | 3,636 req/s, ~92 MB/s, p99 122 ms |

The wire size matches the earlier run, so this is not a bigger response. `/` is still about 330 bytes. `file.jpeg` is still about 26 KB. The JPEG paste stopped at `Requests/sec: 3636.18`; `2.70GB` in `30.08s` is about 92 MB/s.

`wrk` got slower. One connection is about 3,300 req/s instead of 11,000. Eight connections only reach about 5,000, where the pool reached about 25,700, because one thread now does the read, the file, and the send. At 64 connections the 99th percentile is 1.24 s. The pool's 64-connection run stayed near its 8-connection run, since only eight workers were ever in service. This loop accepts all 64, and `poll` inside `Socket::send` holds every other client while one socket's kernel buffer is full.

The median at one connection is still 187 µs. The 4.07 ms average is the tail, up to a max of 136 ms.

The check `wrk` cannot make did go the other way. Eight Python sockets held a keep-alive connection idle, and `curl -w "waited %{time_total}s"` on a ninth request printed `waited 0.001070s`. On the pool that ninth request waited until a worker left `recv`.

These `wrk` rows are from before `EVFILT_WRITE`. At that point a full send buffer still waited inside `poll`.

## What the write registration showed

`Socket::send` now returns after `EAGAIN`. The unsent tail stays on the connection, and `EVFILT_WRITE` wakes `flush` when the kernel can take more. The raw numbers are in `bench.md`. `big.bin` is 3.1 GB.

A client that read 111 bytes of headers and then stopped did not block the loop. `GET /` during that pause printed `waited 0.002968s`. With 30 of those downloads parked, twenty page requests stayed between 0.000243 s and 0.000918 s, and a 10-second `wrk` at 8 connections did 6,612 req/s (p50 0.94 ms, p99 23 ms). That sits next to the 5,026 req/s from the kqueue run with nothing parked.

The slow reader started at those same 111 header bytes and then got 4096 bytes per `recv`, ending at 159,855 bytes. The file moved only when that client read.

The other side is a client that never lets the buffer stay full. `curl` of `/big.bin` took the whole 3167 MB in about 2 seconds, near 1240 MB/s. Page requests overlapped with that transfer waited 0.43 s, 1.78 s, 0.18 s, and 2.22 s. One request after the download had finished waited 0.000292 s. `wrk` for those 2 seconds did 24 req/s, p50 91 ms, p99 1.57 s, 48 requests. `flush` keeps writing until `EAGAIN`. On localhost that client drains about as fast as the server fills, so `kevent` only runs in the gaps.
