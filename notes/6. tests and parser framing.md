# Tests and parser framing

These are my notes on testing the parser and the response builder without a listening socket, and on the `\r\n` bug those tests made obvious.

## The issue

Curl was the only check. A broken status line or a dropped header still required starting the server, sending a request, and reading stderr. The parser and `HTTPResponse` do not touch sockets, so they can be called from a test with a string in and a string out.

The parser also did not match the bytes a real client sends. Two separate mistakes were stacked.

`operator>>` reads the method, path, and version and stops on whitespace. A real request line ends in `\r\n`, and `\r` is whitespace, so the stream is left sitting on that `\r`. The old code then called `ignore()`, which drops one character. That character is the `\r`. The next character is `\n`. `getline` reads up to `\n`, so the first "line" is empty, the loop breaks, and every header is discarded. Keep-alive still appeared to work for curl, because HTTP/1.1 stays open when the `Connection` header is missing. The header was never parsed. The tests written with only `\n` hid this, because `>>` already consumes a lone `\n` as whitespace and `ignore()` then has nothing to do.

The second mistake is the value. `substr` after the colon kept the space, so `Connection: close` was stored as `" close"`, often with a trailing `\r` as well. `handleClient` used `find("close")`, which still matched. An exact compare would not have.

## How the test binary is built

`file(GLOB src/*.cpp)` includes `main.cpp`. Linking that into the tests gives two `main` functions, one from the server and one from GoogleTest. The server sources other than `main.cpp` are built as `http_server_lib`. `http_server` is `main.cpp` plus that library. `http_tests` is `tests/parser_test.cpp`, `tests/response_test.cpp`, the same library, and `GTest::gtest_main`.

GoogleTest 1.15.2 is downloaded by CMake `FetchContent` the first time the build directory is configured. That step needs a network connection. After that:

```bash
cmake --build build
ctest --test-dir build --output-on-failure
```

`--output-on-failure` prints the assertion that failed. A line such as `Expected equality ... Which is: " */*"` means the parser returned the left value and the test expected the right one. `headers["HOST"]` showing `""` does not mean the header was empty. `operator[]` inserts a missing key. The request had `Host`, and the test looked up a different spelling.

GoogleTest is the one piece in this work that really is a separate library. It is not part of macOS and it is not part of the C++ standard library. CMake's `FetchContent` downloads the 1.15.2 sources from GitHub the first time the project is configured. After that, `GTest::gtest_main` supplies the test process's `main`, which finds the `TEST` functions and runs them. `EXPECT_EQ` is a macro from that library. A failed `EXPECT_EQ` records the two values and continues the test. It does not open a socket.

`>>`, `getline`, `peek`, and `ignore` are `std::istringstream`, also the C++ standard library, `<sstream>`. They parse a string that is already in memory. They are not `recv`. The tests pass a string that looks like a request. The parser never sees a file descriptor.

The parser logs each header with `Logger::debug`. The tests never set `LOG_LEVEL`, so the cutoff stays `info` and those lines stay off. That is why `ctest` is quiet.

## What the parser does now

After the request line, if the next character is `\r` it is consumed, and if the next is `\n` it is consumed. A test written with only `\n` still works, because `>>` already ate that newline and both `peek` checks see something else.

Each `getline` result drops a trailing `\r` before the empty-line check. Otherwise the blank line `\r\n` arrives as the string `"\r"`, which is not empty, and the parser would not stop at the end of the headers. A line with no colon is skipped. The value is trimmed of spaces and tabs on both ends. The name is not lowercased, so the key is `Host`.

The old expectations `" localhost"` and `" keep-alive"` had to change to `"localhost"` and `"keep-alive"`, or those tests fail even though the parser is right. `ParsesCrlfHeaders` is the case that used to lose every header. It sends:

```text
GET / HTTP/1.1\r\n
Host: localhost\r\n
Connection: keep-alive\r\n
\r\n
```

`IncompleteRequestLineLeavesVersionEmpty` is a different bug and was left alone. The input is `GET /\nHost: localhost`. There is no version token, so `>>` skips the newline as whitespace and reads `Host:` as the version. Fixing `\r\n` does not invent a version that was not there.

A header with no colon is still skipped. An unknown method such as `FOO` and a version such as `HTTP/9.9` are still returned as-is. The parser does not reject them.

## Response tests, and why chunk framing needed a function

`serialize` and `serializeHeaders` return strings, so the tests do not need a client. Header order in `unordered_map` is not stable. A test that sets both `Content-Length` and `Connection` cannot compare the whole response to one expected string. It searches with `find`. `find("\r\n\r\n") == rfind("\r\n\r\n")` means the blank line appears once. `serializeHeaders` with `Transfer-Encoding: chunked` must not contain the body and must not contain a `Content-Length` that was never set. An empty body means the string ends in `\r\n\r\n`.

The size line, the chunk bytes, and `0\r\n\r\n` used to be written inside `handleClient` and passed straight to `send`. A unit test cannot see bytes that only exist on a socket. `formatChunk` and `chunkTerminator` return those pieces:

```text
formatChunk("Hello")  ->  5\r\nHello\r\n
formatChunk(" World") ->  6\r\n World\r\n
chunkTerminator()     ->  0\r\n\r\n
```

`handleClient` sends the string from `formatChunk` once per read and the terminator once after the file ends. The tests check the strings. They do not open a port.

## What the first `ctest` run showed

The parser was already trimming, and four tests still described the old behavior. The failure text is the thing to read. `Which is:` is what the code returned. The other value is what the test expected.

- `ParsesMultipleHeaders` expected `" localhost:8001"` and `" */*"`. The parser returned `"localhost:8001"` and `"*/*"`.
- `HeaderWithoutColonIsSkipped` expected `" localhost"`. The parser returned `"localhost"`.
- `TrimsHeaderValue` still expected `" keep-alive"`. The name of the test said trim, and the assertion still had the space.
- `ParsesCrlfHeaders` looked up `headers["HOST"]`. The key in the map is `Host`. `operator[]` created `HOST` and returned `""`. The `Connection` check on the next line was fine. The request line and the headers had been parsed.

The response tests in that same run already passed: status line, `Content-Length`, empty body, header block without the body, and `5\r\nHello\r\n` plus `0\r\n\r\n`. Fixing the four expected strings, including the key spelling, is what made the parser file match the parser. The code did not need another change for those failures.
