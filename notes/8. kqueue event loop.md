# Kqueue event loop

These are my notes on why the thread pool stalls, and on `kqueue`, which is a macOS kernel facility I had not used before.

## What is wrong with the server today

The server today spends most of its threads waiting. A kqueue loop lets one thread watch many sockets and run only when one of them has something to do.

### What happens now

The main thread blocks inside `accept()` until a client connects. That connection is handed to one of 8 workers. The worker then blocks inside `recv()` until that client sends bytes, disconnects, or the 2-second timeout fires. While it waits, that worker cannot serve anyone else.

Eight idle keep-alive clients fill the whole pool. A ninth connection sits in the queue even though the other eight are doing nothing. The benchmark showed the other side of the same limit: 8 connections already reach about 26,000 requests/sec on `/`, and 64 connections do not go faster.

### What kqueue changes

`kqueue` is a macOS system call that means "wake this thread when one of these sockets is ready." The listening socket and the client sockets are marked non-blocking, so `accept()` and `recv()` return immediately instead of putting the thread to sleep. If nothing is ready they return an error of `EAGAIN`, and the thread goes back to `kevent()` to wait for the next socket.

One loop then does this:

1. Wait in `kevent()`.
2. If the listening socket is ready, `accept()` until it returns `EAGAIN`, and register each new client.
3. If a client socket is ready, `read()` until `EAGAIN`, append to that connection's buffer, and answer when `\r\n\r\n` has arrived.
4. Repeat.

Hundreds of idle connections cost a list of file descriptors, not a blocked thread each. The 8 workers stop being the cap on how many clients can be connected at once.

### What it does not change

It does not make `file.jpeg` faster to read from disk. The 207 ms tail on that file is time spent moving about 26 KB per response. Kqueue removes waiting on idle sockets. It does not remove the cost of sending a large body.

The first version should be only non-blocking `accept` and `read`. Chunked writes can stay as they are until the read side is solid. Writing is the next step, because a non-blocking `send()` can also return after only some of the bytes are written.

## Why `recv()` blocks when the response itself is fast

The request itself is quick. The worker is blocked during the quiet time after the response, and during any wait before the next bytes arrive.

`recv()` does not return until the kernel has at least one byte, the client closes, or the 2-second timeout fires. The worker thread is asleep inside that call. It cannot take another connection from the queue.

With keep-alive, a browser opens one connection and then pauses. The timeline on one worker looks like this:

```text
0 ms     recv() returns the GET / request
1 ms     server sends index.html
1 ms     recv() is called again, waiting for the next request
...
500 ms   the browser asks for /file.jpeg
501 ms   server sends the image
501 ms   recv() waits again
...
2000 ms  no more bytes, recv() returns -1 (timeout), loop calls recv() again
```

For almost that whole 2 seconds the worker owns the socket and does nothing. Eight browsers that have already received their page, and have not asked for anything else yet, occupy all 8 workers. A ninth browser's connection is already accepted into the queue, but no worker is free to read it.

`wrk` hides this because it sends the next request immediately on the same connection. The 75 µs result from the single-connection benchmark is the busy case. A real client spends most of the connection idle, and that idle `recv()` is what holds the worker.

Without keep-alive this particular stall would not happen. The worker would close the socket after one response and return to the pool, so an idle client could not hold it. A worker could still block while that one request was being read or sent, but only for that request.

## How to see the stuck workers

To see it, hold 8 connections open so every worker is stuck in `recv()`, then ask for a ninth page. The ninth request sits in the queue until one of the first eight is closed.

Start the server, then run this in a second terminal. It sends one request on each socket and then sleeps, which keeps the connections idle:

```bash
python3 - <<'PY'
import socket, time
socks = []
for _ in range(8):
    s = socket.create_connection(("127.0.0.1", 8001))
    s.sendall(b"GET / HTTP/1.1\r\nHost: localhost\r\nConnection: keep-alive\r\n\r\n")
    s.recv(65536)
    socks.append(s)
print("8 workers are now waiting in recv()")
time.sleep(60)
PY
```

While that is sleeping, in a third terminal:

```bash
curl -w "waited %{time_total}s\n" -o /dev/null http://127.0.0.1:8001/
```

That `curl` does not finish. The server already accepted it, but all 8 workers are inside `recv()` on the Python sockets, so nobody reads the ninth request. Stop the Python program with Ctrl+C. One worker returns from `recv()`, takes the queued connection, and `curl` prints a wait of many seconds.

A normal `curl` with no Python sockets returns in about a millisecond. The delay appears only when the pool is full of idle connections.

## How the same worker stays on the same client

The worker does not recognize the client later. It never lets go of that client's socket, so the next bytes can only be from the same TCP connection.

`accept()` returns a new file descriptor for one connection. That descriptor is moved into the task, and one worker runs `handleClient` with that `Socket`. The loop at the bottom does not exit after a normal HTTP/1.1 response. `shouldClose` is false, so it does not `break`. Execution goes back to the top of `while (true)` and calls `recv()` on the same descriptor.

The kernel already knows which bytes belong to which connection. Bytes sent by that browser are queued on that descriptor and nowhere else. The worker is not matching an IP address or a cookie. It is blocked in `recv(this socket)`. Whoever sends the next request on that connection is, by definition, the same client.

A browser loading a page looks like this on one worker:

```text
accept() gives socket 7 to worker 2

worker 2: recv(7) waits
browser:  GET / HTTP/1.1 ... Connection: keep-alive
worker 2: recv returns those bytes, sends index.html
worker 2: Connection is keep-alive, so it does not close socket 7
worker 2: recv(7) waits again

browser, same connection: GET /style.css HTTP/1.1
worker 2: recv returns that second request, sends the file
worker 2: recv(7) waits again
```

Socket 7 stays open in worker 2 the whole time. Worker 3 never sees this browser. If the browser then asks for `/style.css`, those bytes arrive on socket 7 because the browser reused the TCP connection instead of calling `connect()` again.

The connection ends only when `recv` returns `0` (the browser closed it), the client sent `Connection: close`, or shutdown is set. Then `handleClient` returns, the `Socket` destructor closes descriptor 7, and worker 2 goes back to the task queue for a different connection.

## Plan for the change

The idle keep-alive connection is the problem. A kqueue loop fixes it by waiting on many sockets at once, using only calls that are already part of macOS and of this server.

### The issue

After a keep-alive response, the worker calls `recv()` again on that same socket and sleeps there until the next request. Eight such connections occupy all eight workers. A ninth connection is accepted and queued, but nobody is free to read it. The request itself is fast. The idle wait is what holds the thread.

### The solution

Stop dedicating a thread to each connection. One thread asks the kernel which sockets are ready, then only reads those.

The listening socket and each client socket are set non-blocking. `accept()` and `recv()` return immediately with `EAGAIN` when there is nothing to do, instead of sleeping. `kqueue` sleeps once for the whole set. When it wakes, the loop accepts new clients or appends bytes to that client's buffer. When a buffer contains `\r\n\r\n`, the existing parse-and-respond path runs, and the socket stays registered so the next request on that connection wakes the same loop later.

The thread pool is not what watches sockets anymore. The first version can still build and send the response on the loop thread after a request is complete. Non-blocking `send()` is a later step. This first step only makes `accept` and `read` non-blocking.

### What is already available

Nothing new has to be installed. There is no extra library and no extra binary. `kqueue` is already in the operating system.

| Piece | Role |
| --- | --- |
| `kqueue()` and `kevent()` in `<sys/event.h>` | Create the queue and wait for ready sockets. `EVFILT_READ` means "readable." |
| `fcntl(..., O_NONBLOCK)` | Make `accept` and `recv` return instead of blocking. |
| `EAGAIN` / `EWOULDBLOCK` | The "nothing ready" result from a non-blocking call. |
| `Socket` | Already wraps the listening socket and the accepted sockets. It needs a `setNonBlocking()` method. |
| `HTTPParser`, `FileServer`, `HTTPResponse` | Unchanged. They run only after one full request is in the buffer. |
| `requestBuffer` | Becomes one buffer per connection, not one local string inside a worker. |

### The flow after this change

```text
start()
  create listening socket, bind, listen
  set it non-blocking
  kqueue()
  register the listening socket for read

loop:
  kevent() waits until any registered socket is readable

  if the listening socket is ready:
    accept() until it returns EAGAIN
    set each new client non-blocking
    register that client for read
    give it an empty request buffer

  if a client socket is ready:
    recv() until it returns EAGAIN
    append those bytes to that client's buffer
    if the buffer contains \r\n\r\n:
      parse one request, send the response, keep leftover bytes
      leave the socket registered unless Connection: close
    if recv() returns 0:
      drop that connection and its buffer
```

An idle keep-alive client stays in the kqueue registration and consumes no thread. The loop thread is free to accept and read the ninth client while the first eight are quiet.

## What is implemented

`HTTPServer::start` creates a kqueue, marks the listening socket non-blocking, and registers it for read. `kevent` is the wait. A readable listening socket calls `acceptReady`, which accepts until `EAGAIN` and registers each client. A readable client calls `readReady`, which reads until `EAGAIN`. `handleOneRequest` parses one complete request and stores the outgoing bytes, and the open file when the body is streamed. `flush` writes until `EAGAIN`. The write filter stays on only while bytes remain. `writeReady` resumes that tail. `Logger::access` runs when the response has been accepted. `Connection: close`, a failed send, or `recv` returning 0 removes the connection. Ctrl+C still sets `g_stop` and shuts down the listening socket, which wakes `kevent`. The map is then cleared, which closes the client sockets.

`Socket::send` returns the count the kernel accepted. `EAGAIN` after a partial copy returns that count. `EAGAIN` with nothing copied returns `-1` and leaves `errno` set. The old `poll` wait inside `send` is gone. The `ThreadPool` is still constructed and is not given connections.

## What the write checks showed

I held `big.bin` (3.1 GB) open and stopped reading after the headers. The first `recv` was 111 bytes, the status line and the chunked headers, and none of the file. A concurrent `GET /` printed `waited 0.002968s` and returned the 225-byte page. Thirty of those parked sockets left twenty more page requests between 0.000243 s and 0.000918 s. A 10-second `wrk` at 8 connections during that pause did 6,612 req/s, p50 0.94 ms, p99 23 ms. The earlier kqueue run with nothing parked was 5,026 req/s. The full send buffer now waits in `kevent`, so those idle downloads did not take the thread.

A slow reader confirmed the file was not being pushed ahead of the client. Forty reads began at 111 bytes and then returned 4096 each, and stopped at 159,855 bytes.

A client that kept reading did occupy the thread. `curl` of `/big.bin` finished all 3167 MB in about 2 seconds, near 1240 MB/s. Page requests during that transfer waited 0.43 s, 1.78 s, 0.18 s, and 2.22 s. After it finished, one page request waited 0.000292 s. `wrk` for the 2 seconds of a second eager download did 24 req/s, p50 91 ms, p99 1.57 s, 48 requests. `flush` writes until `EAGAIN`. That client drained the buffer about as fast as it was filled, so the loop only served `/` in the gaps. The detail is in `bench.md`.

## What the same checks showed

These `wrk` numbers are from the loop before `EVFILT_WRITE`, when a full send buffer still waited in `poll`. I reran the commands from `bench.md` and the eight-idle-socket check. `LOG_LEVEL` was unset. Each `wrk` run was 30 seconds against `127.0.0.1:8001`.

The ninth request, while eight Python sockets sat idle after one keep-alive response, printed `waited 0.001070s`. On the pool that curl did not finish until a worker left `recv`. The idle stall is gone.

`wrk` moved the other way. It never leaves a connection quiet, so it measures the one loop thread against the eight workers:

| Target | Connections | Thread pool | kqueue |
| --- | --- | --- | --- |
| `/` | 1 | 10,992 req/s, p50 75 µs, p99 1.34 ms | 3,269 req/s, p50 187 µs, p99 56.66 ms |
| `/` | 8 | 25,694 req/s, p50 265 µs, p99 3.86 ms | 5,026 req/s, p50 1.17 ms, p99 39.44 ms |
| `/` | 64 | 24,693 req/s, p50 261 µs, p99 1.13 ms | 3,236 req/s, p50 14.75 ms, p99 1.24 s |
| `/file.jpeg` | 8 | 21,708 req/s, 549 MB/s, p99 207 ms | 3,636 req/s, ~92 MB/s, p99 122 ms |

Eight busy connections only reach about 5,000 req/s, against about 25,700 before. The loop finishes one response before it serves the next ready socket. At 64 connections the tail becomes 1.24 s, because all 64 are accepted and a full send buffer waits in `poll` inside `send`. The pool never had more than eight sockets in service, so its 64-connection throughput stayed near the 8-connection number.

`file.jpeg` drops from 549 MB/s to about 92 MB/s. The 99th percentile shortens from 207 ms to 122 ms. One response is not the regression. Only one file is being read and sent. That matches the earlier note that kqueue does not make the file faster to read, and it shows the extra cost of doing that read on the only thread.

## Where `kqueue` comes from

I did not know this call existed. It is not a third-party package and it is not something added on top of the project. `kqueue` and `kevent` are system calls provided by the macOS kernel, declared in `<sys/event.h>`. The server process asks the kernel to create a queue and then to sleep until one of the sockets in that queue is readable. The kernel updates the queue when a network packet arrives. The C++ code never touches the queue directly. It only sees the result `kevent()` returns.

Linux has the same idea under another name, `epoll`. Windows has `IOCP`. The registration and wait calls differ, but each one is the kernel telling a process which of its sockets are ready. A `kqueue` program does not run on Linux without a different wait call.

The queue itself lives in kernel memory, attached to a file descriptor that `kqueue()` returns. That descriptor is just a handle, like the listening socket. The CPU does not poll it in a loop of its own. The path is:

```text
a packet arrives on the network card
the kernel's network code finds the socket that packet belongs to
the kernel marks that socket readable and notes it on the kqueue
a thread that is inside kevent() is woken
that thread, the event loop, runs again and calls accept() or recv()
```

While nothing is ready, the loop thread is not running. It is blocked inside `kevent()`, the same way a worker used to be blocked inside one `recv()`, except this wait covers every registered socket. When the kernel wakes it, the thread runs on a CPU core only long enough to read the ready sockets and go back to sleep. The sockets that are idle never wake it, so they do not need a worker thread each.
