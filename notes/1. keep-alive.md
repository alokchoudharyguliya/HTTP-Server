# Keep-alive

These are my notes on serving more than one request on the same TCP connection, and on why the worker does not have to "recognize" the client afterward.

## What came before

The first change in this area was the opposite of keep-alive. Every response set `Connection: close`, `handleClient` broke out of its loop after one send, and the `Socket` destructor closed the descriptor when the function returned. A browser that needed `/` and then `/style.css` had to open a second TCP connection.

That was a deliberate one-request-per-connection step. The response looked like:

```text
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 125
Connection: close

<html>...</html>
```

`Socket::send` was also only one `::send` call. The kernel may accept fewer bytes than were passed, so closing immediately after that call could cut the response off. `send` now loops until `sentTotal == length`. `EINTR` retries the same offset. A return of 0 or any other error returns -1, and `handleClient` does not treat that as success. The socket still closes when the `Socket` object goes out of scope. There is no separate `close` call on the success path.

## The issue keep-alive has to solve

HTTP/1.1 leaves the connection open unless the client sends `Connection: close`. HTTP/1.0 does the reverse: it closes unless the client sends `Connection: keep-alive`. The server has to decide that per request, tell the client in the response, and only then either loop or break.

Two other facts are easy to miss:

- The client has to know where this response ends before it sends the next request. At this stage that was `Content-Length`. Chunked encoding came later and replaced it for files.
- One `recv` can already contain the next request. Wiping `requestBuffer` after the first response throws those bytes away.

## How the same worker stays on the same client

The worker does not look the client up by address. `accept` returns one file descriptor for one TCP connection. That descriptor is moved into the task, because `Socket` is move-only, and one worker runs `handleClient` with it. After a normal HTTP/1.1 response `shouldClose` is false, so the loop does not `break`. It goes back to the top and calls `recv` on that same descriptor.

The kernel already queues bytes per connection. The next `GET` arrives on this descriptor only if the browser reused this TCP connection instead of calling `connect` again.

```text
accept() gives socket 7 to worker 2

worker 2: recv(7) returns GET /
worker 2: sends index.html with Connection: keep-alive
worker 2: does not close socket 7
worker 2: recv(7) waits

browser, same connection: GET /style.css
worker 2: recv returns that second request and sends the file
worker 2: recv(7) waits again
```

Socket 7 stays with worker 2. Worker 3 never sees this browser. The connection ends when `recv` returns 0, the client sent `Connection: close`, send fails, or shutdown is set. Then `handleClient` returns and the destructor closes the descriptor.

## The decision in code

```text
connection = request.headers["Connection"]
shouldClose if connection contains "close"
shouldClose if version is HTTP/1.0 and connection does not contain "keep-alive"
response Connection is "close" or "keep-alive" to match
if shouldClose, break, else loop
```

`find("close")` is used rather than comparing the whole string. Before the parser trimmed values, the stored text was `" close"` or `" close\r"`. A substring search still matched. After trimming, the value is `close` or `keep-alive`, and the same check still works.

This first version only treats a GET with no body as complete at `\r\n\r\n`. A POST body would continue past that marker and is not framed yet.

## Leftover bytes

Headers are accumulated until `\r\n\r\n`. A single `recv` is not assumed to contain a whole request, and it is also not assumed to contain only one request:

```text
GET / HTTP/1.1\r\nHost: localhost\r\n\r\nGET /style.css HTTP/1.1\r\n...
```

`headerEnd` is the index of that marker. `consumed` is `headerEnd + 4`, which includes the four bytes `\r\n\r\n`. `parse` is given only `substr(0, consumed)`. Parsing the whole buffer would walk into the next request's header lines and treat them as part of this one. `erase(0, consumed)` leaves the rest. If nothing was left, the buffer is empty and the next loop blocks in `recv`, which is the idle keep-alive wait.

`requestBuffer.clear()` was the old line. It is wrong once more than one request can share a read.

## Where the socket and `recv` come from

A TCP connection is not something the C++ code invents, and it is not a library added to the project. `socket`, `bind`, `listen`, `accept`, `recv`, and `send` are POSIX system calls. On macOS they live in the kernel and are declared in headers such as `<sys/socket.h>` and `<unistd.h>`. The C++ `Socket` class only stores the integer file descriptor those calls return and forwards to them.

The kernel, not `handleClient`, owns the byte queues. When the browser writes a request, the network stack appends those bytes to the receive queue of that one connection. `recv` copies from that queue into the process. If the queue is empty, the calling thread sleeps inside the kernel until bytes arrive, the peer closes, or the receive timeout fires. `send` copies the other way, into the kernel's send queue. A short return means the kernel accepted only part of what was offered, which is why `Socket::send` loops. `EINTR` means a signal interrupted the call before it finished. That is also a kernel report, not an HTTP error.

`Connection: keep-alive` is not one of those calls. It is a header defined by HTTP. The server decides to call `recv` again. The kernel's only role is to keep delivering bytes on the same descriptor for as long as the TCP connection stays open.

## How I read the curl output

```bash
curl -v --http1.1 http://localhost:8001/ http://localhost:8001/ http://localhost:8001/ http://localhost:8001/
```

Only lines that start with `*`, `>`, or `<` matter. The HTML is the file body and can be skipped. `>` is what curl sent. `<` is what the server sent. `*` is curl talking about the connection.

The proof is three lines:

- `Connected to localhost (127.0.0.1) port 8001` appears once. A new TCP connection would print `Connected` again.
- `< Connection: keep-alive` is on every response.
- `Connection #0 to host localhost left intact` and then `Re-using existing connection with host localhost` appear before requests 2, 3, and 4. `#0` is the first socket.

The IPv6 line at the top, `connect to ::1 port 8001 failed: Connection refused`, is a failed attempt before that one success. The server listens on IPv4 only. `</html>` showing up next to "left intact" is the body and the verbose log overlapping, not a second response.

The default port in `main` is 8001, not 8000, unless a port is passed on the command line.
