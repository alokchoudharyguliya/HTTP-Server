# Logging

These are my notes on why debug text moved off `cout`, and on the cutoff that decides which `Logger` lines are printed.

## The issue

Two problems were stacked.

Workers handle requests at the same time. `std::cout` is not locked, so two workers writing the raw request and the header map could mix characters on one line. Those prints also had no timestamp and no level, and they went to stdout while `Logger` writes stderr. A line on stdout and a line on stderr are not ordered with each other.

`Logger` already locked every write with `mutex_`. The missing piece was that the debug prints in `handleClient` did not use it. The ones that were still live were "Received", the raw buffer, and each header printed as `name<value`. The startup line "Server is listening on port ..." duplicated `Logger::info`, which already prints "Listening on port". An old `std::cout << "Worker exiting"` sat after the worker's `while` loop. The loop returns from inside, so that line never ran. The real exit already logs `Worker thread exiting`.

The second problem showed up once those prints went through `Logger::debug`. Every debug call still formatted and wrote, including one line per header. Parser tests and a normal run became noisy, and the `wrk` benchmark would have spent time logging instead of serving. There was no way to keep the calls and hide them.

## Moving the prints

The live `cout` calls in `handleClient` became `Logger::debug`. The duplicate listening line was removed rather than logged twice. The unreachable worker print was removed rather than turned into a second exit line. Commented-out `cout` lines were left as comments. They do not run.

Every real line now goes to stderr, takes `mutex_` for the duration of the write, and has the prefix `[timestamp] [LEVEL]`. The lock is what stops two workers from interleaving mid-line. It does not make the lines sorted by the time the request happened. It only makes each line whole.

## The cutoff

`Logger::Level` is an `enum class` with the order `debug`, `info`, `warning`, `error`. The stored cutoff `level_` defaults to `info`. `enabled` is `level >= level_`. Because of the declaration order, `warning >= info` is true and `debug >= info` is false. That comparison is the whole filter.

`debug`, `info`, `warning`, and `error` return before taking the mutex when the line is below the cutoff. `access` does not call `enabled`. It is the request record, not a severity, so a request line is printed at every level, including `error`.

`main` reads `LOG_LEVEL` with `getenv` before the port is parsed and before `HTTPServer` is constructed, so the invalid-port error and the startup lines obey it. `setLevelFromString` accepts `debug`, `info`, `warning`, and `error`. Anything else leaves the cutoff at `info` and calls `warning`, which is visible because the cutoff is still `info`.

| `LOG_LEVEL` | What is printed |
| --- | --- |
| unset or `info` | info, warning, error, and every access line |
| `debug` | those, plus debug |
| `warning` | warning, error, and every access line |
| `error` | error and every access line |

The string passed into `Logger::debug` is still built at the call, even when debug is filtered. The filter skips the lock and the write. It does not skip the concatenation. That is acceptable here. It would matter if a debug line did expensive work before the call.

## Where the level and the lock come from

`Logger` is code in this project. It is not a logging library that was installed. The lock is `std::mutex` from the C++ standard library, `<mutex>`. `lock_guard` locks it for the rest of the block and unlocks when the block ends, including when the function returns. The mutex does not talk to the kernel's socket queue. It only stops two threads of this process from writing `cerr` at the same time.

`std::cerr` is the C++ stream for standard error. The shell shows it in the same terminal as the program. It is a different stream from `std::cout`, which is why the old debug prints and the logger lines were not one ordered sequence.

`LOG_LEVEL` is not read from a config file. `std::getenv`, from the C library, reads the process environment. The shell puts `LOG_LEVEL=debug` into that environment before it starts the program. If the variable was never set, `getenv` returns null and the cutoff stays at the default `info`. The comparison `level >= level_` works because `enum class Level` lists `debug`, then `info`, then `warning`, then `error`. That order is the C++ language rule for enumerators, not a table stored anywhere else.

## What I saw

```bash
./build/http_server
LOG_LEVEL=debug ./build/http_server
LOG_LEVEL=error ./build/http_server
LOG_LEVEL=nope ./build/http_server
```

With no variable, startup `info` lines remain and there is no `DEBUG` line for "Client Connected" or the raw buffer. `LOG_LEVEL=debug` brings those back, one header per line. `LOG_LEVEL=error` drops the startup `info` lines and keeps `ACCESS` and `ERROR`. `LOG_LEVEL=nope` prints the unknown-level warning and then behaves as `info`.

`ctest` stays quiet on the parser's header lines because the tests never set `LOG_LEVEL`, so the cutoff stays `info`. The benchmark was run the same way on purpose. Debug logging would have been part of the time being measured.
