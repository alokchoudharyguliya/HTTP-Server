# Path traversal

These are my notes on why joining the request path onto `public/` is not enough, and on how a resolved path is checked before the file is opened.

## The issue

Only the exact path `/` is special. It becomes `documentRoot_ + "/index.html"`. Every other path was string concatenation:

```text
filePath = documentRoot_ + request.path
```

The request line `GET /../../etc/passwd HTTP/1.1` therefore becomes the string `public/../../etc/passwd`. Nothing in the server looks at the `..` segments. `FileServer::exists` and `openBinary` pass that string to the operating system. `..` means the parent directory, so the open walks out of `public/`, up to the directory that contains it, and then to `/etc/passwd`. If that file exists and this process may read it, the old code sent it back with status 200. If it does not exist, the client got the ordinary 404. The server could not tell a missing page from an escape, because both were just "open failed."

A path that stays inside the root by accident is not the same check. `GET /etc/passwd` is stored as `/etc/passwd`, and concatenation produces `public/etc/passwd`, which is still under `public/`. The dangerous case is `..`, and also a symlink that lives inside `public/` but points outside it.

## What `weakly_canonical` does

After `filePath` is built, both it and the document root go through `std::filesystem::weakly_canonical`. That walks the path, removes `.` and `..`, and follows symlinks for the prefix that exists. `canonical` was the wrong call here. It throws if the final file does not exist, and a missing page inside `public/` is a normal 404, not an error in the check.

`public/../../etc/passwd` resolves to `/etc/passwd`. `public/index.html` resolves to something that still starts with the absolute form of `public/`.

The comparison is not a raw `starts_with(root)`. The root string gets a trailing `/` when it does not already end with one. The file is inside only when the resolved path equals the root, or when it starts with that root-plus-slash.

```text
rootText = ".../public/"
".../public/index.html"   inside
".../public"              inside, equal to the root
".../public-secret/x"     not inside
"/etc/passwd"             not inside
```

The slash is the part that is easy to miss. Without it, `public-secret` starts with the letters `public` and would be treated as inside the document root.

The open still uses the original `filePath`, not a rewritten string. That is safe only because the check ran on the canonical form of that same string. If the check failed, `openBinary` is not called.

## Where `weakly_canonical` comes from

`weakly_canonical` is not a macOS call and it is not a package. It is `std::filesystem::weakly_canonical`, from the C++ standard library, declared in `<filesystem>`. This project already builds as C++20, which includes that library. Nothing extra is installed to resolve a path.

The function still asks the operating system to look up the directories. `..` and `.` are directory entries the kernel understands: `..` is the parent, `.` is the directory itself. A symlink is a file the kernel replaces with another path when the file is looked up. `weakly_canonical` walks those, builds the absolute path, and if the final component does not exist it still returns the normalized form of the prefix that does. That is the "weakly" part. `std::filesystem::canonical` is the stricter function in the same header. It fails if the full path does not exist, which would turn a normal missing page into an exception instead of a 404.

The trailing-slash compare after that is ordinary string logic in this server. The library does not know what a document root is. It only returns the resolved path. The server decides whether that path is still inside `public/`.

## 403 instead of reusing 404

The first version of the check sent the escape down the existing missing-file path, so the client saw 404 and the log said "File not found" for a path that was never supposed to be opened. That hides whether the check worked. The two cases are now split:

- Outside the root: status 403, reason `Forbidden`, body `<h1>403 Forbidden</h1>`, log `Rejected path outside the document root`.
- Inside the root but not opened: status 404, body `<h1>404 Not Found</h1>`.

The access log counts those bodies. 403 is 21 bytes. 404 is 22 bytes. The file is not part of that count, because it was not read.

A symlink inside `public/` that points at `/etc/passwd` fails the same check. `weakly_canonical` follows the link, the resolved path is `/etc/passwd`, and `insideRoot` is false, so the link is not opened.

## What this does not decode

The parser stores the path bytes as they arrived. `%2e%2e` is the characters `%`, `2`, `e`, not the two characters `.`. The filesystem will not treat that as a parent directory, so this check does not have to. Turning percent-escapes into real characters would be a separate change, and it would have to happen before `weakly_canonical`.

## How I tested it

Curl removes `..` itself before the request is written, unless `--path-as-is` is set. A plain `curl http://localhost:8001/../../etc/passwd` never reaches the server as `..`, so it does not test the check.

```bash
curl -v --path-as-is http://localhost:8001/../../etc/passwd
curl -v http://localhost:8001/
curl -v http://localhost:8001/no-such-file
```

The first is 403 and the body is the forbidden page, not the contents of `/etc/passwd`. The second is still 200. The third is 404 with `Content-Length: 22`.
